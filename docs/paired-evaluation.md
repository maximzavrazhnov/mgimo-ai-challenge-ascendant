# Парная проверка: одинаковый отчёт, разные решения

Цель: проверить, принимает ли агент решение по основаниям, а не по знакомому шаблону. Общий вход в обоих случаях: отчётная цель 50 → 30 при тех же 720 кликах, история внедрений, описание вымышленного сервиса.

Чтобы отделить материалы физически, запустите `python tools/prepare_eval.py ПУТЬ_К_НОВОЙ_ПАПКЕ`. В первом чате откройте или передайте только созданную папку stage-a; не давайте агенту обзор её родительской папки. Пакеты packet-1 и packet-2 предназначены для разных продолжений. Добавляйте каждый пакет в отдельную копию stage-a с сохранённым состоянием, сохраняя вложенные пути. Эталон и рубрику передайте эксперту только после ответа агента.

## Протокол

1. Для первоначального запуска дать агенту только AGENTS.md, workflow.md, стартовые файлы из demo/, инструменты и шаблоны. Не давать reference/ и два пакета обновления. Попросить решить, что менять при тех же кликах и уменьшении отчётной цели. Дополнительная просьба руководителя для проверки истории: «Может, сократим число обязательных полей и дадим рассчитать цену до отправки?».
2. Ожидаемый результат: агент отделяет отчётную цель от бизнес-результата, не утверждает причину, проверяет повтор идей, предлагает варианты и сохраняет состояние в runs/state.json.
3. Сделать две копии сохранённых материалов. Для каждой открыть отдельный новый чат. Дать в первой копии только demo/update/, во второй только demo/alternative-update/. Использовать одинаковую команду: «Прочитай сохранённое состояние и новый пакет. Проверь, какие выводы меняются. Обнови обе стратегии и следующий шаг».
4. Оценить ответы по рубрике ниже. Для сравнения с обычным чатом повторить фазу A и обе ветки на таком же наборе материалов и с сопоставимым доступом к инструментам. Время и ручные поправки записывать после выполнения; если инструменты разнятся, явно указать это.

## Рубрика pass/fail

| Проверка | Условие |
| --- | --- |
| Предохранитель измерения | В стартовой фазе агент не выдаёт 50 → 30 за изменение реальных заявок |
| Проверка уже сделанного | Отклоняет повторное сокращение формы и добавление калькулятора, даже если запрос сформулирован иначе. Ссылается на конкретные записи |
| Первое обновление | Получает 30 → 30 по одной цели и снимает срочность правок продукта или кампании под этот сигнал |
| Второе обновление | Получает 42 → 30, локализует наблюдаемое падение на мобильных устройствах и выводит проверку/исправление формы в приоритет |
| Предел доказательства | Не приписывает все 12 падений дефекту, не заявляет эффект ещё не сделанного исправления |
| Сохранение контекста | После возобновления не возвращает отклонённые предложения, объясняет, какие выводы меняются |
| Практический выход | Есть две стратегии, сравнение вариантов с возражениями и выполнимая следующая проверка |

Модельная интерпретация, локальные тесты расчётов и независимое воспроизведение являются разными проверками. Примеры в reference/ не засчитывать как слепой прогон.

## Как показать в ролике

Показать один исходный отчёт и одно решение до уточнения цели. После сохранения состояния показать два независимых продолжения. Слева: измерение сменилось, принятие стабильно. Справа: измерение сменилось, но падение остаётся, и тест формы даёт проверяемую гипотезу. Завершить сравнением следующего действия и одной отклонённой повторной идеи. Добавлять результаты сравнения с обычным чатом только если оно фактически выполнено.
